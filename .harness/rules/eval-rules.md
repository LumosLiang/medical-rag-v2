# 评测规则

改检索配置、标注或评测代码之前读这一份。

## 什么时候必须跑

改动下面任何一项都要跑 `RUN_EVAL`,提交说明里附 run_id 和结论:

- 解析参数
- 切分逻辑或参数(`sql/20_chunk.sql`、PIPELINE_CONFIG 里的切分字段)
- 检索服务定义(`sql/40_search.sql`)或检索参数
- 检索模块

## 标注

- 每题标 (question, doc_id, evidence 原文片段, 题型, 过滤条件),不标 chunk_id。块是否相关按"是否包含 evidence"判定,容忍空白、连字符和页眉插入。改切分不用重标。
- 四类题型均衡:语义、关键词、实体、带过滤。每题要有明确指代,不能出现"this case"这种没有对象的说法。
- 先做 30 题让流程跑起来,再扩到 60 题以上。
- 标注用 CREATE OR REPLACE … VALUES 装载,重跑不会产生重复题目。

## RUN_EVAL 的步骤

前一步不过,后面不跑。

1. 最近一次数据检查全部通过,而且之后没有新的入库批次。
2. evidence 匹配规则的固定用例(空白、连字符、页眉插入)全部通过。
3. 每题的 evidence 至少被当前块表里的一块完整包含。不满足的题列出来并判失败,不静默算成未命中;evidence 跨两个块时也在这一步暴露。这一步只做校验,不计分。
4. 逐题检索并测延迟,结果写表。相关性用检索结果里返回的原文列判断,不去读块表。
5. 在同一标注集上算 Recall@1/3/5/10、MRR、p50/p95 延迟,块级和文档级各一份。
6. 和基线比:MRR 绝对下降超过 0.02 判失败。v1 观察到检索排序有非确定性,第三位小数不可信。

## 每次运行记录什么

git sha、配置名、完整配置、标注版本、语料快照(文档数,以及 (路径, etag) 列表的哈希)。

## 和谁比

只和标注版本、语料快照都相同的上一次通过的运行比。入库是事件驱动的,语料随时会变:语料一变,先重跑一次基线,否则分不清指标变化来自配置还是语料。v1 和 v2 的指标不可比。

## 和入库分开

- 评测只通过检索服务读语料;唯一的例外是第 3 步的校验。
- 指标参数(K 值、返回条数等)放在评测自己的表里,不放进 PIPELINE_CONFIG,免得改切分参数时顺带改了指标的算法。
